Benchmarking { honest numbers }

bench_common.hpp: warmup, median timing with steady_clock, and full-array verify before trusting speedup.

01

Shared harness

  • time_microseconds(fn) — warmup, then timed runs; returns median/min/max µs. Fn&& is a forwarding reference (accepts temporary lambdas).
  • verify_float_ranges — absolute tolerance per element (vecadd, axpy, …).
  • verify_float_exact / verify_int32_exact — bit/integer identity.
  • verify_scalar_close — relative tolerance for reductions (dot, sum).
  • kDefaultSize = 10'000'007 — large work unit; not a multiple of 4/8 so the remainder loop runs.

Speedup printed as baseline_us / fast_us (e.g. Scalar / SIMD).

02

Warmup & median

Default: 3 warmup (not timed) + 10 timed iterations. Each fn() already processes ~10M elements — few outer repeats, large inner work. Median after sort resists one noisy sample better than a single timing or a mean.

Not production profiling

For serious work use perf, Instruments, or Google Benchmark with pinned CPU frequency. This lab uses chrono for a small self-contained harness.

03

steady_clock

Elapsed intervals need a monotonic clock. system_clock can jump (NTP). high_resolution_clock is not required to be steady (on Apple libc++ it aliases steady_clock). The harness uses std::chrono::steady_clock and converts (t1-t0) with duration<double, micro>.

04

Fair scalar baseline

At -O3 with native ISA flags the compiler auto-vectorizes simple loops. Scalar functions use SIMD_SCALAR_NO_VEC so speedup compares hand intrinsics vs true scalar — not vs compiler-SIMD.

05

Correctness first

A fast wrong kernel is useless. Pattern:

  1. Scalar reference → expected (untimed).
  2. Time scalar and SIMD (often writing into result; SIMD overwrites last).
  3. Compare full arrays / scalars with an appropriate checker.
  4. Exit code 1 on failure — CTest.

For in-place AXPY, reset from y_orig every run; verify one clean shot so timing mutations do not confuse the check. Reductions: SIMD may differ slightly from scalar without a logic bug — use relative tolerance.

06

Interpreting speedup

ExerciseTypical storyWhy

branchless / clipCan look huge in this labScalar optnone + branch cost vs tight NEON
Read README results carefully

Sample NEON speedups in the README (e.g. ~9× vecadd, ~20× threshold) use the lab’s disabled-autovec scalar. They show the intrinsic path is fast and correctness passes — not that you will get the same ratio against production -O3 scalar or BLAS.

Numbers depend on CPU, power state, and background load. Treat speedups as relative on a given machine.

07

Revision checklist

Q Why steady_clock?

Monotonic — safe for elapsed Δt. system_clock can jump; high_resolution_clock is not required to be steady.

Q Absolute vs relative verify?

Element-wise kernels: absolute / exact. Reductions (dot, sum): relative — float add order differs.

Q Why median of 10, not one timing?

Caches, turbo, OS noise. Warmup first; median resists a single spike.
