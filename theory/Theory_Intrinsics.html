Every exercise under src/ follows the same skeleton: detect backend, SIMD main loop in steps of lane count, scalar tail, verify against baseline. See 01_vecadd.cpp.

01

Backend detection — simd_detect.hpp

CMake passes -march=native (x86) or -mcpu=native (ARM). The compiler defines __AVX2__ or __ARM_NEON, which gates includes and intrinsics.

include/simd_detect.hpp (pattern)
#if defined(__AVX2__)
    #include <immintrin.h>
    #define SIMD_BACKEND_AVX2 1
#elif defined(__ARM_NEON) || defined(__ARM_NEON__)
    #include <arm_neon.h>
    #define SIMD_BACKEND_NEON 1
#else
    #define SIMD_BACKEND_SCALAR 1
#endif

SIMD_FLOAT_LANES is 8, 4, or 1. SIMD_SCALAR_NO_VEC marks scalar baselines so the compiler does not auto-vectorize them — essential for honest speedup numbers (Clang: optnone; GCC: no-tree-vectorize).

02

The core loop pattern

src/01_vecadd.cpp (AVX2)
constexpr std::size_t step = 8;  // lanes
std::size_t i = 0;
for (; i + step <= n; i += step) {
    __m256 va = _mm256_loadu_ps(a + i);
    __m256 vb = _mm256_loadu_ps(b + i);
    __m256 vr = _mm256_add_ps(va, vb);
    _mm256_storeu_ps(out + i, vr);
}
for (; i < n; ++i)          // remainder
    out[i] = a[i] + b[i];

NEON is identical in structure with step = 4, float32x4_t, vld1q_f32, vaddq_f32, vst1q_f32. Reductions keep an accumulator across iterations instead of storing each chunk (see Reductions & FMA).

Pointer form a + i is the same as &a[i] for contiguous storage. Kernels take float* + length so they work with vector::data(), raw arrays, or aligned buffers.

04

Remainder loop

Array length is rarely a multiple of 8 (or 4). The main loop condition i + step <= n processes full chunks only. The tail loop handles n % step leftovers with scalar code.

Bug pattern

Skipping the tail when n % step != 0 leaves the end of the output wrong. Overshooting (SIMD past n) reads/writes out of bounds. Every exercise uses kDefaultSize = 10'000'007 (not divisible by 4 or 8) so the remainder path always runs.

Example n = 10, step = 8: one SIMD chunk for indices 0–7, then scalar for 8 and 9.

05

Alignment

std::vector<float> is contiguous and aligned for float (typically 4 bytes), not for AVX’s 32-byte aligned loads. Default in this lab: loadu / storeu.

  • 32 bytes = width of one AVX float vector (8 × 4). Aligned load wants the address divisible by 32.
  • 16 bytes = NEON float vector width. AlignedFloatBuffer defaults to 32 so both ISAs are covered.

std::aligned_alloc requires the byte size to be a multiple of the alignment; aligned_alloc.hpp rounds up.

06

Pitfalls

✕

Wrong step size

Using 4 on AVX2 float or 8 on NEON — wrong chunk sizes or out-of-range lanes.

✕

In-place without reset

AXPY (03) mutates y. Timing without restoring y_orig accumulates αx every run.

✕

Wrong ISA binary

Build with native flags on the machine you run on. An AVX2 binary on a CPU without AVX2 faults.

✕

FMA argument order

AVX fmadd(a,b,c) = a*b+c; NEON vfmaq(c,a,b) = c+a*b. Mixing them silently wrongs AXPY/dot.

07

Revision checklist

Q Write the SIMD loop skeleton in one breath.

i=0; while i+step <= n: load → compute → store, i+=step; then scalar for i < n.

Q Why i + step <= n and not i < n for the SIMD loop?

Guarantees a full chunk of step elements remains. Using i < n alone with a fixed step would overshoot.

Q Why loadu with std::vector?

Vector data is contiguous but not guaranteed 32-byte aligned. Aligned load_ps would be UB on a misaligned pointer.

Q What does SIMD_SCALAR_NO_VEC do?

Stops the compiler auto-vectorizing the “scalar” baseline so speedup is intrinsics vs true scalar.
